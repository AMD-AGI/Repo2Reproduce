# CUDA-to-ROCm kernel porting

The experiment must run the paper's GPU computation on ROCm with the paper's algorithm,
numerical formats, and hyperparameters unchanged. Porting is part of preparing the
environment, not a reason to block. The stage prompt says whether the run is in standard or
forced-kernel mode, which host tools exist, and how the porting record must be returned.

## Ground rules

- **No PyTorch fallback.** Every CUDA kernel the selected entrypoint launches must run on
  ROCm as a GPU kernel written in HIP, Triton, Composable Kernel, or rocWMMA. This includes
  preprocessing and postprocessing kernels (quantization, mean subtraction, scaling,
  packing, layout transforms, fused epilogues), however cheap they look. PyTorch may only
  allocate inputs, call the ported entrypoint, implement the parity reference, and run the
  full-precision baseline. A PyTorch implementation of a kernel's math, including eager
  tensor operations, SDPA, or `torch.compile` of them, is never a port, even when the
  repository already contains it.
- **No PyTorch hipify.** Never call `torch.utils.hipify` or `hipify_python`, and never let
  `torch.utils.cpp_extension.CUDAExtension` translate sources during the build (it runs
  `torch.utils.hipify`). Translate with the official HIPIFY tool the run provides. The build
  log must contain no `torch.utils.hipify` output (lines mapping a source to a `_hip` copy
  that end in `[ok]` or `[skipped, ...]`).
- **Generated copies are disposable.** The HIPIFY-translated copy is regenerated by the tool
  and loses edits made inside it. Keep every source change in a patch file or idempotent
  edit script under the host workspace, applied by the Dockerfile or launch script on top
  of the translated copy.
- **The paper's kernel is what gets measured.** For latency, throughput, or memory targets,
  the timed call must reach the ported kernel. Cite evidence that it did (call counts,
  profiler kernel names, or a control experiment) rather than assuming it.

## Procedure

### 1. Inventory before choosing

Run the run's scanner and HIPIFY tool on the clone before deciding anything. From their
reports and the code, list every CUDA kernel the selected entrypoint launches (follow the
Python call into the extension and every kernel its launcher starts), and for each one note
its blockers: inline PTX, CUTLASS/CuTe, warp-size assumptions, shared-memory size,
CUDA-only headers or libraries, and compute-capability dispatch. Every blocker or high
finding needs an explicit decision recorded in the attempt evidence.

### 2. Walk the strategy ladder in order

| Strategy | Use when | Counts as success when |
| --- | --- | --- |
| `existing_rocm_port` | An official ROCm fork, upstream ROCm support, or a ROCm build of the dependency exists | It runs the same computation on ROCm |
| `portable_repo_path` | The repository already has a Triton or other GPU-kernel path for the same computation, including non-default paths and paths that fail only because a package eagerly imports a CUDA extension | It is a GPU kernel, not PyTorch math |
| `hipify_with_fixes` | Sources translate with HIPIFY and the leftovers are fixable | The translated sources build with hipcc and pass parity |
| `targeted_rewrite` | Translation cannot be fixed (inline PTX tensor-core code, CUTLASS/CuTe device code) | Only the kernels the experiment calls are rewritten, with the original numerics, starting from the translated host code |

In standard mode, stop at the first strategy that gives a working path to the selected
result. In forced-kernel mode, the first two are investigation and parity references only;
success requires `hipify_with_fixes` or `targeted_rewrite`. Record every strategy you tried
or ruled out with concrete evidence: URLs, file paths, commands, compiler errors.

Choosing between the two kernel strategies: kernels without PTX or CUTLASS usually need
only HIPIFY plus a few hand fixes. Kernels built on `mma.sync`, `ldmatrix`, `cp.async`,
`<cuda_pipeline_primitives.h>`, or CUTLASS/CuTe templates usually go straight to a rewrite,
most cheaply in Triton (`tl.dot` maps to MFMA). Rewrite only what the experiment launches;
keep data formats, packing, and accumulation precision identical.

### 3. Fix what HIPIFY leaves behind

HIPIFY translates CUDA runtime and library calls but silently leaves several things. Work
through [gfx942-reference.md](gfx942-reference.md) for the mappings and recurring fixes:

- PyTorch's C++ CUDA API (`ATen/cuda/...`, `at::cuda::`, `c10::cuda::`, `C10_CUDA_*`);
- `__CUDA_ARCH__` checks;
- warp-width assumptions: gfx942 wavefronts have 64 lanes;
- shared-memory limits: 64 KiB of LDS per workgroup;
- NVIDIA-only compiler flags, missing headers, and API overload differences.

Fix semantics, not only spelling. Use compile and runtime feedback: a kernel that compiles
with a 32-bit lane mask on a 64-lane wavefront is still wrong.

### 4. Build correctly

Compile the translated sources with hipcc. For PyTorch extensions use `CppExtension` with
`BuildExtension` (which compiles `.cu`/`.hip` sources with hipcc) and add the include
directories, libraries, and macros `CUDAExtension` would have added; alternatively use
CMake, Make, or hipcc directly. The image build has no GPU to detect, so set the target
architecture explicitly. See the build recipe in the reference file.

### 5. Prove numerical parity

Before the ported path counts as working, compare it with a trusted reference on identical
random inputs:

- **Reference:** the repository's reference implementation, an established library, or the
  paper's algorithm written in plain PyTorch. The reference is only compared against; it
  never replaces the ported kernel in the smoke test or the final launch.
- **Inputs:** the selected experiment's dtypes and shapes, not toy sizes.
- **Error metric and tolerance:** choose a metric where lower is better (max absolute
  error, relative L2, mismatch fraction for discrete outputs such as codebook indices) and a
  tolerance justified by the dtype and the operation, decided before looking at the result.
- **Evidence:** save the complete comparison log under the run's artifacts. An observed
  error above tolerance means the port is not finished.

### 6. Record the port

The stage prompt names the fields. Content rules:

- The summary says what was ported or substituted and why the result still reflects the
  paper.
- Each strategy appears once, with its outcome and concrete evidence.
- Each launched CUDA kernel appears once among the ported kernels: its name exactly as
  written in the CUDA source, that source file, the implementation language, and the files
  that define the replacement kernel (`__global__`, `@triton.jit`, `ck::`, or `rocwmma::`).
- Every patch or edit script is listed.

## Repairing a ported run

When an execution fails on a path that contains ported kernels:

- Never regress a ported kernel to PyTorch, to the repository's reference path, or to a
  disabled extension. Fix the port or its build instead.
- Never drop a kernel from the porting record; a repaired record still lists every kernel
  the entrypoint launches.
- If kernel source, build flags, or the image change, re-run the parity check on the same
  inputs and tolerance and record the new observed error and log.
- Keep new source changes in patch files, as in preparation.

## Blocking honestly

Block on a CUDA reason only after every applicable strategy was tried and recorded. In
forced-kernel mode both kernel strategies must have been actually attempted. A kernel that
was ported and verified, followed by a block on an unrelated CUDA-only third-party library,
is a valid outcome: name the library, the import chain, and why it is not the paper's
contribution.
